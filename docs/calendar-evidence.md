# Calendar evidence — 2026-09-20

KASI 공식 역서에서 독립 전사한 날짜·일진 15건과 절기 6건을 구현 실행 전에 `tests/domain/calendar-evidence-fixtures.ts`에 고정했다. 대응 테스트는 29개 통과했다. 이는 전 생년 범위의 천문 검증이나 12종 acceptance 각각의 완전한 사주 4주 정답 인증은 아니다. M8 판단식 수작업 검증은 별도 [fixture review](saju-fixture-review.md)를 따른다.

1992 음력9월29일=10월24일, 癸酉는 원문 월초에서 **28일을 수작업으로 더한 파생 기대값**이다. 원문 직접 전사와 구분한다. 진태양시 사례는 당일 남중에서 시간차를 추정한 시지 검증이며 약 41분 이상의 경계 여유가 있다. 모든 시각의 EoT 정밀 검증으로 확대해 해석하지 않는다.

시간대 근거는 [IANA Asia의 ROK 규칙](https://data.iana.org/time-zones/tzdb/asia), [North America의 US 규칙](https://data.iana.org/time-zones/tzdb/northamerica)이다. 확인 당시 [tzdb version](https://data.iana.org/time-zones/tzdb/version)은 `2026d`; URL은 최신본으로 바뀔 수 있어 fixture에 읽은 규칙 문자열과 버전을 함께 기록했다. 한국은 1988-05-08 02:00에 한 시간 전진, 10-09 03:00에 후퇴한다. 미국은 2007년부터 3월 둘째 일요일 02:00에 전진, 11월 첫째 일요일 02:00에 후퇴하는 규칙을 사용한다. 해당 날짜는 이 정의로 도출했다. IANA 파일 스스로 역사 자료의 비권위성과 오류 가능성을 명시한다.

## 남은 검증과 실행

전 범위 달력, 절기 초 단위, 해외 출생 4주, 과거 법정 시간 원문, 대운 정밀 시작일, 실제 Supabase Edge의 시간 모름 CPU 측정은 이번 자료로 완료 처리하지 않는다. 합화·신살·강약·용희신은 관측 천문값이 아니라 승인된 제품 규칙이므로 별도 수작업 fixture를 검증한다.

```sh
node node_modules/vitest/vitest.mjs run tests/domain/calendar-evidence.test.ts
```

기대값은 구현에서 생성하지 않았고 실패 후 허용차나 표를 바꾸지 않았다. 29개 통과는 위 한정된 근거의 재현 결과다.

14개의 유효 입력 모두 Full 원국을 DB에 저장한 후 `SAJU_INTERPRETATION_FAILED` / `LLM_UNAVAILABLE`로 **PARTIAL**을 반환했다. 해석 성공·실제 LLM 품질 통과로 세지 않는다. API·snapshot·DB 열의 engine/rule/convention 세 버전 일치를 확인했다. 시각 미상은 시주·시주 십성을 null로 유지했고, 각 flat 확정 기둥은 correlated charts의 공통값과 일치했다. 입춘 미상은 `癸卯/乙丑/丁酉`, `癸卯/乙丑/戊戌`, `甲辰/丙寅/戊戌` 세 조합만 저장됐다. 독립 후보들의 Cartesian product를 만들지 않았다.

당시 배포의 현재 대운은 `UNRESOLVED`이므로 시각이 알려진 경우도 `LIMITED`였다. 이 실행을 Full 결과 전체가 `COMPLETE`였다고 표시하지 않는다. wall-time은 클라이언트에서 인증·도시 검증·Edge·DB·해석 실패 반환까지 잰 시간이다. **CPU 시간·플랫폼 사용량·부하 내구성 측정은 아니다.** 실제 Edge에서 이 15개 입력을 처리했다는 사실은 확인했으며, 배포 변경 후 재검증과 CPU 계측은 별개다.

성공 실행의 임시 사용자 3개를 모두 삭제하고 해당 profile/reading 행 0개를 재조회했다. 초기 준비 단계 두 번은 `New York` 검색이 다른 동명 지역을 반환해 계산 전에 중단됐고, 해당 임시 사용자 6개도 모두 삭제·cascade 검증했다. 검색어를 `New York City`로 고쳐 공식 resolver가 반환한 providerId와 좌표/시간대 스냅샷을 그대로 사용했다. 기본 limit=8 검증은 유지했다. 계정 이메일·비밀번호·토큰·원시 사용자 식별자는 보고서에 포함하지 않는다.
