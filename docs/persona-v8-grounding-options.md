# v8 근거 검증 구조 대안 — 읽기 전용 제안

2026-09-20, Codex AI / fortune_audit. 구현·원본 corpus 변경·실모델 호출0이다. v7 micro8은 1차9.0/HF0와 독립9.25/HF1의 차이를 보존하며 **FAILED**로 유지한다. 다음 설계는 특정 은둔자 문장을 정답으로 박거나 같은 금지문을 계속 덧붙이는 방식이 아니다.

## 현재 확인된 문제

현재 모델은 ID/방향/위치 reference를 정확히 복사하면서도 본문에 다른 방향의 의미를 넣을 수 있다. v6은 선택 방향의 keyword 배열을 제공했고, v7은 같은 자료를 위치·방향과 연결한 한국어 근거문까지 제공했다. 그런데 `10:SANI`는 “혼자만의 시간이 필요하거나 상황을 피하고 싶은”이라는 대안을 함께 썼다. 현재 deterministic validator는 참조 tuple을 검증하며, 자연어의 필요성/원인 주장이 선택 방향과 맞는지까지 보증하지 않는다.

`고립` 같은 정확한 키워드를 본문에 한 번 포함시키는 것만으로도 해결되지 않는다. 키워드 뒤에 반대 원인을 덧붙이거나, 올바른 내용을 인용하면서 부정할 수 있다. 추가 구조는 어떤 사실을 검증하고 어떤 의미 판단을 남기는지 분리해야 한다.

## ① 원래 정·역 의미의 대조 projection

각 카드의 승인된 두 배열에서 다음을 **동일 함수로** 파생한다.

- `selected`: 선택 방향·원래 keywords·현재 위치.
- `otherDirection`: 선택되지 않은 방향의 원래 keywords. 비교 자료임을 별도 field로 구분.
- `selectedOnly`, `otherOnly`, `shared`: 문자열 동등성에 따른 집합 차이/교집합. 동의어·감정 가치·새 사주/타로 판단을 넣지 않는다.

선택 방향과 일반 카드 이미지를 구분하기 쉬워진다는 가설이다. 기존 keyword를 다시 해석하거나 `정방향=좋음/역방향=나쁨`으로 변환하지 않는다. 어떤 카드에도 동일한 구조를 적용한다.

위험은 **선택되지 않은 의미를 입력에 다시 노출**한다는 점이다. 이전 projection은 그 배열을 제거했으므로, 잘못된 방향을 더 자주 섞을 가능성도 있다. 은둔자의 반대 배열에는 성찰·거리두기·탐색·독립·깊이가 있으나 실제 실패 표현 “혼자 있을 필요”가 그대로 적혀 있지는 않다. 그러므로 `otherOnly` 문자열 출현을 금지하는 검사는 이 실패를 확실히 잡지 못하며 정/역 비교 요청도 잘못 막을 수 있다.

장점은 현재 응답 schema·화면·provider를 바꾸지 않는 작은 실험이다. 단점은 새 입력 설명일 뿐 검증 구조가 생기지 않는다는 점이다. **이 대안만으로 의미 검증이 생겼다고 주장하지 않는다.**

## ② 내부 evidence-first 응답과 정확한 근거 연결

원본 의미에 안정적인 내부 key를 부여한다. key는 `meaningVersion/cardId/orientation/keywordIndex`처럼 현재 row를 식별할 뿐 의미를 새로 생성하지 않는다. 모델은 최종 본문과 함께 자신이 사용한 카드/키워드와 본문의 근거 span을 반환한다.

```text
interpretationEvidence[] = {
  positionIndex,
  selectedKeywordIndices[],
  textEvidence  // 최종 text 안에 실제 존재하는 연속 원문
}
```

서버는 다음을 기계적으로 검증할 수 있다.

1. 참조 카드·위치가 저장된 draw에 존재하고 source version이 일치하는가.
2. keyword index가 그 카드의 **선택된 방향 배열** 안에 있는가.
3. `textEvidence`가 최종 본문에 실제 존재하는가. 모델이 근거 문장을 따로 만들어 놓고 본문에는 다른 말을 쓰지 않았는가.
4. 필요한 경우 선택 keyword 자체가 연결된 span 안에 있는가. 미존재 index·다른 카드·누락/중복 근거·가짜 span은 repair 또는 거절 사유가 된다.

이 단계는 **traceability와 근거 누락**을 검사한다. span이 keyword를 부정하는지, 실제 상대의 마음으로 단정하는지, 원인을 뒤집는지는 여전히 자연어 의미 문제다. 같은 올바른 keyword를 끼워 넣은 모순 문장은 통과할 수 있다. 그런 반례를 unit fixture에 포함해 deterministic 검사 범위를 과장하지 않아야 한다.

필드가 provider 내부에만 머물면 기존 API의 사용자 text/toolReferences를 유지할 수 있다. 다만 provider schema와 validator·repair는 변경된다. 모든 응답에 세 카드 해석을 강제하면 사용자가 카드 하나만 묻는 상황에서 불필요한 길이를 만들 수 있어, 어떤 해석 span에 어떤 evidence를 요구할지는 실제 질문 범위를 보존하도록 별도로 정해야 한다. “상담 말투”로 표시된 문단에 검증되지 않은 점술 주장을 숨기는 우회도 고려해야 한다.

추가 모델 왕복 없이 구조만 확장할 수 있으나 output tokens가 늘고 schema 불이행·repair가 증가할 수 있다. 기존900 output 상한을 먼저 유지하고 실제 빈 content·잘린 JSON·추가 tokens를 계측해야 한다. 구조 통과를 원본 semantic acceptance 통과로 대체하지 않는다.

## ③ 생성 뒤 별도 의미 검증 모델

생성 답변을 사용자에게 표시하기 전에 별도 검증 호출에 **원래 선택 방향 facts, 현재 질문의 최소 맥락, 생성 본문**만 보낸다. 과거 전체 기억이나 원시 출생정보는 필요하지 않다. 생성 답변은 검증기에게 지시가 아니라 검사 대상 데이터다.

검증 출력은 보수적인 enum 결과와 원문 근거를 요구할 수 있다.

```text
decision: CONSISTENT | CONTRADICTORY | UNCERTAIN
issues[]: {cardRef, draftQuote, canonicalKeywordIndices, issueType}
```

`draftQuote`가 실제 본문에 있는지, source reference가 맞는지는 서버가 확인한다. 검증기가 인용이나 규칙을 만들어내면 그 검증을 PASS로 처리하지 않는다. 카드 방향·대상·확률 날조 등을 한 번에 무한히 검사하도록 맡기기보다는, 우선 원본 선택 방향과 본문의 모순이라는 한정된 계약을 평가한다.

검증 모델도 오류가 있다. 같은 Gemma가 생성과 검증을 맡으면 공통 오해가 그대로 반복될 수 있다. 이미 시험한 같은 Cloudflare의 다른 모델을 쓰면 모델 간 상관은 줄 가능성이 있지만 품질·가격·latency가 별도로 필요하며 검증 성공을 미리 가정할 수 없다. 새로운 외부 processor나 유료 모델은 이 제안에 포함하지 않는다.

**비용:** 현재 시험에 쓰는 [공식 Gemma 단가](https://developers.cloudflare.com/workers-ai/platform/pricing/)(input9091/output27273 neurons per million)라면 검증 input1500/output150 tokens라는 *예시 가정*에서 약17.73 neurons/건이다. 실제 측정치가 아니며84건이면 약1489.11 neurons가 추가된다. 각 실제 요청에는 여전히 bytes-as-tokens/최대 output 예약이 필요하다. correction과 재검증을 하면 비용이 더 늘어난다. 검증에 보낼 facts의 크기·출력 상한을 0-network preflight로 먼저 계산해야 한다.

**지연:** 모델 왕복이 한 번 이상 더해진다. 기존 생성·schema repair·intent 분류가 이미 전체 요청 deadline을 공유하므로, 단순히 검증 timeout을 덧붙이면 lease를 초과할 수 있다. 전체 잔여 deadline에서 검증과 최대 한 번 correction/재검증을 배분하고, 시간이 부족하면 새 호출을 시작하지 않는 구조가 필요하다. 실제 p50/p95는 검증 프로토타입 이후에만 말할 수 있다.

**실패 처리:** CONTRADICTORY/UNCERTAIN/timeout/잘못된 검증 JSON을 조용히 PASS로 넘기면 알려진 오류 차단 목적을 잃는다. 기존 저장 draw를 유지하고 해석 재시도 상태로 끝내는 방식이 가장 작은 기존 흐름 재사용안이다. 거절된 답변을 화면에 먼저 스트리밍하면 안 된다. 별도의 정형 keyword fallback을 사용자에게 보이려면 “모델 해석”과 “저장된 카드 기본 자료”를 구분해야 하며 별도 제품 선택이 필요하다. 과도한 검증 실패는 가용성을 낮추므로 실제 false positive도 측정해야 한다.

## 제안 순서와 검증 자료

우선②의 **순수 검증 구조**를 로컬에서 설계해 무엇을 잡고 놓치는지 명확히 하는 것이 유용하다. 이것이 본문 의미를 보증하지 못한다는 반례까지 고정한 뒤, 필요하면③을 추가하는 경로가①만 반복하는 것보다 실제 검증 기능을 만든다. ①은 저비용 입력 대조 실험으로 남길 수 있지만, 효과와 반대 의미 오염 위험을 따로 본다. 이 선택은 아직 구현 승인이 아니다.

소규모 평가에는 기존10B/S/A, 정방향 대비, YOUR/THEIR 교환,09악마RISK, A/B 및 사주 경계 사례를 그대로 쓸 수 있다. 추가 **검증기 전용** fixture는 사실상 같은 출력의 다른 라벨을 암기하게 하기보다 다음 유형을 구분해야 한다: 틀린 source ID, 반대 방향 index, 존재하지 않는 본문 span, 올바른 keyword를 담은 부정문, 올바른 keyword와 반대 원인이 함께 있는 문장, 사용자가 정/역 비교를 요청한 문장, 실제 관찰 정보와 상징을 구분한 문장.

1차와 독립 리뷰가 갈린 혼합 대안의 판정 기준은 두 판단을 보존하고 Main이 적용 기준을 정한 다음에 검증기 기대를 고정해야 한다. 특정 버전이 통과하도록 원본 corpus나 점수 기준을 바꾸지 않는다. 어느 구조를 택해도 마지막에는 원본 core60+supplement24 직접 의미 검토가 필요하다. 현재는 설계만 제출하고 추가 source 변경·실호출 없이 기다린다.
